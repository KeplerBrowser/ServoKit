# Servokit Embedded Surface Contract

## Intent

This document defines the Servo 0.3-aligned embedded-surface contract: layout
hosts can embed a Servo surface through the `servokit` facade while keeping
ownership of their app windows and layout trees. The current surface modes and
lifecycle rules for `NativeChildSurface`, `CpuOffscreenSurface`, and future
`GpuLayerSurface` live in
[`surface-modes.md`](./surface-modes.md).

The forcing case is GPUI, because a GPUI app generated by
`create-gpui-app` owns `Application::run`, opens its own `Window`, and renders a
layout tree. Servokit therefore has to embed Servo into an app-owned layout
region, not create a competing top-level window. The same contract also covers
the current `examples/desktop-winit` path and the existing React Native Android
`ServoView` path.

## Ownership rule

Servokit owns Servo webview/delegate/embedder-control/render integration behind
facade and host seams. The application owns platform and framework ergonomics.

**Servokit must not own top-level application windows, menus, tabs, or app event
loops.** A host adapter may allocate render resources for an embedded webview,
but the app decides when the app starts, which top-level windows exist, where
the webview appears in layout, which menus/tabs/chrome exist, and when the
native event or frame loop calls back into Servokit.

## Contract

An embedded Servo surface is a Servo webview attached to an app-owned
window or app-owned layout slot. The host must provide these pieces to the
Servokit facade/host implementation:

| Area | Contract |
| --- | --- |
| App-owned layout/window | The app creates the top-level window and layout tree. Servokit receives a `HostSurface`/surface identity plus host callbacks for a specific layout slot. A whole-window webview is only the degenerate case where the slot equals the window content bounds. |
| Native or offscreen surface | The host supplies either a native child/window surface that Servo can render to, or an offscreen rendering target that the host composites into the layout slot. Native handles remain app/host-owned and valid until detach. |
| Size and viewport | The host reports the embedded slot size in physical pixels through `SurfaceSize`-equivalent values and sends resize when GPUI/winit/RN layout changes. The host maps the slot bounds in app coordinates to Servo viewport coordinates. If layout collapses to zero, the host should withhold attach or detach until a nonzero size is available. |
| Scale factor | The host passes display density / HiDPI scale separately from physical size. Scale changes must update Servo via the webview scale path before the next paint. |
| Update and present hooks | The app's event/frame loop calls Servokit update pumping. Servokit spins Servo, observes delegate paint requests, paints when needed, and calls a host-provided present/composite hook. Servokit does not run the app loop itself. |
| Input and focus | The app hit-tests its layout. Pointer, wheel, touch, keyboard, IME, and focus events that belong to the embedded slot are translated into Servokit `HostInputEvent` / host-specific input paths with coordinates relative to the slot. App shortcuts and surrounding UI can consume events before forwarding. |
| Event draining | After attach, resize, commands, input, and updates, the app drains Servokit events and maps them to framework callbacks or chrome updates. Servo delegate policy requests stay in Rust pending state and resolve through the controller seam rather than through a platform view lifetime. |
| Embedder controls | Servo webview delegate requests for navigation policy, dialogs, context menus, select/file pickers, permissions, fullscreen, cursor, focus, crash/error, and similar embedder-control events are converted into shared Servokit events. The control coordinator owns request identity, fallback/timeout policy, and response validation; the app owns user-facing UI for those controls. |
| Lifetime | The control handle may outlive an attached render surface. Detach removes the render target but does not by itself invalidate browser control identity or release the root runtime lease. Dropping or destroying the owning root webview/host invalidates later commands and releases that lease. |

Servo-backed paths retain `ProcessServoRuntime` on its owning UI thread and
permit one active `ProcessServoRuntimeLease`/live root. A later root reuses that
runtime after dropping or destroying the owning root webview/host releases its
lease. See
[Architecture](../ARCHITECTURE.md#current-servo-runtime-limit).

Lower-level Rust ServoKit supports root-scoped `PopupRequestPolicy::ManagedChild`
and managed-child surface lifecycle. React Native Android instead uses
default-deny and exposes `onCreateNewWebViewRequested` only as informational
host-routed intent; it does not create, present, or adopt those children. iOS
does not emit that React Native event.

## Current Servo and ServoKit APIs

Current Servo APIs already expose the primitives needed for this contract:

- `servo::WebViewBuilder::new(&servo, Rc<dyn RenderingContext>)` builds a
  `WebView` against an embedder-provided rendering context, not an internally
  owned app window. The builder accepts `.delegate(...)`,
  `.clipboard_delegate(...)`, `.url(...)`, and `.hidpi_scale_factor(...)`.
- `servo::WebView` exposes the browser operations Servokit already wraps:
  `load`, `reload`, `go_back`, `go_forward`, `focus`, `blur`, `resize`,
  `notify_input_event`, and `paint`.
- `servo::Servo::spin_event_loop()` lets the host pump Servo from the app's
  frame/event loop.
- `servo::WebViewDelegate` exposes the event and policy surface Servokit is
  already translating: new-frame-ready, URL/title/status/load/history/focus,
  cursor, fullscreen, crash, navigation policy, permissions, and embedder
  controls. Popup/new-window intent maps to `request_create_new`; main-frame
  and iframe navigation allow/deny maps to `request_navigation`;
  `load_web_resource` is HTTP/HTTPS resource interception or alternate response
  loading, not popup routing.
- `servo::WindowRenderingContext::new_with_refresh_driver(display_handle,
  window_handle, size, refresh_driver)` accepts `raw-window-handle` display and
  window handles supplied by a host. It also supports `resize`, `present`,
  `take_window`, and `set_window` for attach/detach-style host lifecycles.
- `servo::OffscreenRenderingContext`, created from a `WindowRenderingContext`,
  renders into an offscreen framebuffer and supports `read_to_image` plus a
  parent blit callback. That is the proof path for layout hosts that cannot or
  should not give Servo a child native window.

Current Servokit code follows the same shape:

- `crates/servokit/src/lib.rs` reexports the facade vocabulary:
  `Runtime`, `SessionHandle`, `WebViewHandle`, `WebViewCommand`,
  `HostInputEvent`, `ServokitEvent`, `HostSurface`, and `SurfaceSize`.
- `crates/servokit-embedder/src/runtime.rs` models attach/resize/detach,
  browser commands, host input dispatch, update pumping, and event draining
  without depending on React Native or a particular windowing toolkit.
- `crates/servokit-embedder/src/servo_webview.rs` is already the reusable
  Servo webview wrapper: it owns `WebViewBuilder`, scale updates, resize,
  command/input dispatch, `Servo::spin_event_loop`, paint, and the host
  `present` callback.
- `crates/servokit-embedder/src/servo_webview_adapter.rs` owns Servo
  `WebViewDelegate` translation and pending embedder-control state.

## Host comparison

| Host | What owns the window/layout? | Surface proof | Update/present proof | Input/event proof |
| --- | --- | --- | --- | --- |
| GPUI | The app calls `Application::new().run`, `App::open_window`, and renders a root `Render` tree. Servokit must be an element/controller inside that tree. | `examples/desktop-gpui` uses GPUI layout bounds plus the GPUI window's raw AppKit handle to supply a child `NSView` for the Servo region, then attaches that child through `servokit::surface::NativeChildSurface`. | GPUI owns redraw scheduling. The example pumps Servokit from a GPUI task, updates the child `NSView` frame during layout/prepaint, and lets Servokit/Servo present into that native child surface. | GPUI layout and hit-testing decide which events reach the element. The example forwards in-slot pointer/keyboard/wheel/focus events to `HostInputEvent` and drains Servokit URL/load/title/focus/input state back to GPUI chrome. |
| `winit` | `examples/desktop-winit` owns `EventLoop::run_app`, `ApplicationHandler`, and the app `winit::Window`. | The example implements `servokit::surface::SurfaceDelegate`, returns borrowed raw display/window handles through `servokit::surface::NativeChildSurface`, and attaches a `HostSurface`/`SurfaceViewport` through `servokit::runtime::Runtime<servokit::surface::SurfaceHost<_>>`. | `about_to_wait` and facade wake events call `Runtime::perform_updates`; Servokit paints and presents through the surface facade. | Example-local code translates `winit` pointer/keyboard/wheel/IME/focus events into `HostInputEvent` values and drains `ServokitEvent` values to stdout. |
| React Native Android | React Native owns the component tree and Android `ServoView`/`SurfaceView`; Servokit does not own the `Activity`, app window, or RN event loop. | `SurfaceHolder` callbacks attach/resize/detach an Android `Surface`; Rust converts the `ANativeWindow` to an `AndroidNdkWindowHandle` for Servo. | Android `Choreographer` calls `performUpdates`; the Android backend spins Servo, paints, and presents through the Android `WindowRenderingContext`. | `MotionEvent`, focus, IME, dialogs, menus, pickers, permissions, and RN callbacks are adapted by Android/RN glue while shared events come from Servokit. |

## GPUI forcing case details

The `create-gpui-app` template proves the required app-owned shape:

```rust
fn main() {
    Application::new().run(|cx: &mut App| {
        cx.open_window(WindowOptions::default(), |_, cx| {
            cx.new(|_cx| HelloWorld { text: "World".into() })
        })
        .unwrap();
    });
}
```

The template also shows the root view implementing `Render` and returning GPUI
elements. Therefore a GPUI Servokit example must render a Servokit element
inside GPUI layout instead of letting Servokit open a `winit`/servoshell-style
window.

The current GPUI sources provide enough host-side hooks for a proof example:

- `gpui::Window` implements `HasWindowHandle` and `HasDisplayHandle`, and exposes
  `scale_factor()`, viewport size, and layout/window state.
- GPUI elements can observe layout `Bounds<Pixels>` during prepaint, so the
  Servokit slot can know the exact region GPUI assigned to it.
- On macOS, the example uses `servokit::surface::macos::AppKitChildSurface` to
  create/update an AppKit child `NSView` under the GPUI window's parent
  `NSView`, size it from GPUI layout bounds plus scale factor, and hand the
  borrowed child-surface handles to the `servokit::surface::SurfaceHost`
  surface facade.
- GPUI event hooks forward pointer, wheel, keyboard, and focus events for the
  slot into Servokit `HostInputEvent` values, while Servokit events update GPUI
  chrome.

This keeps GPUI as the app/layout owner and Servokit as the Servo embedder owner.
The low-level child-`NSView` helper now lives in Servokit as the macOS-gated
`servokit::surface::macos::AppKitChildSurface` API, so app/framework adapters
can reuse the same CEF-like child-surface embedding glue without taking a GPUI
dependency.

## Facade implications

The facade keeps the existing runtime path and exposes the feature-gated
`servokit::surface::SurfaceHost` surface host for layout embedders:

1. The app creates a `servokit::runtime::Runtime<servokit::surface::SurfaceHost<_>>`,
   session, and webview through `servokit`.
2. The app or framework adapter implements `servokit::surface::SurfaceDelegate`
   for an app-owned layout slot.
3. The host attaches a `HostSurface` plus `SurfaceViewport` (origin, physical
   size, and scale) when the layout slot has a valid native child/window target
   or an offscreen target that the host will composite.
4. Layout changes call viewport updates through the Servokit runtime so size and
   scale reach Servo together before any update/present work.
5. App/frame-loop callbacks call update pumping; Servokit paints and hands the
   current `SurfaceFrame` to the host's present/composite callback.
6. Framework input handlers translate in-slot input to Servokit input.
7. Delegate events are drained and reflected in app state; policy responses use
   the controller/delegate seam, not ad hoc view commands.

A whole-window `winit` example remains valid as the simplest surface attachment,
but GPUI proves the facade must also work when the embedded surface is a child
layout region with independent bounds. Applications own those windows/layouts;
Servokit owns Servo webview/delegate/embedder-control/render integration behind
the public facade.

## Non-goals and risks

- This document does not introduce a production GPUI component crate or a new
  zero-copy compositor.
- Exact GPUI zero-copy texture integration is still platform-specific. The
  AppKit child-view path is sufficient to prove the contract, but it may not be
  the final performance path.
- GPUI is pre-1.0. `examples/desktop-gpui` currently uses crates.io `gpui`
  0.2.2 with the `runtime_shaders` feature.
- Servo's `WindowRenderingContext::set_window`/`take_window` APIs are marked in
  Servo as temporary until webviews can replace rendering contexts. Current
  Android hosts and the `winit` example use this lifecycle pattern, but future
  Servokit code should follow upstream API changes.
